# 프로젝트 아이디어: 화면 주석 레이어 (투명 필름 주석)

핸드폰에서 **현재 화면에 바로 펜으로 주석을 달고**, 페이지별로 기억·토글할 수 있는 기능/앱 아이디어 정리.

---

## 1. 아이디어 요약

### 현재 불편한 점
- 스크린샷으로 이미지 저장 → 갤러리/그림판 앱 열기 → 그 위에 그리기 → 저장
- **일련의 과정이 길고**, 원본과 분리되어 관리되기 어려움

### 제안하는 방식
- **핸드폰 옆 주석 버튼**을 누르면 → **현재 페이지에 바로 펜으로 주석** 가능
- **지우기를 누르지 않는 한** 그 페이지에 주석이 **달린 채로 유지**
- **원본 손상 없음**: 페이지 **맨 위에 투명 필름 같은 레이어**가 있고, 그 **필름 위에만** 주석을 다는 구조
- **페이지별 기억**: 투명 필름이 **그 페이지를 기억**하고 있어서, **해당 페이지에서만** 주석이 활성화
- **토글**: 핸드폰 옆 버튼으로 투명 필름(주석 레이어)을 **보이기/숨기기** 가능

---

## 2. 핵심 개념 정리

| 구분 | 내용 |
|------|------|
| **레이어** | 현재 화면 최상단에 투명한 “필름” 레이어가 있음 |
| **입력** | 사용자는 그 필름 위에만 펜으로 그림/글 작성 |
| **원본** | 아래 실제 페이지(앱 화면)는 전혀 수정되지 않음 |
| **연결** | 필름은 “현재 페이지(URL/화면 ID)”와 1:1로 연결됨 |
| **표시** | 같은 페이지에 다시 들어오면 해당 필름(주석)만 그 페이지에서 보임 |
| **토글** | 버튼(또는 다른 방식)으로 필름 표시/비표시 전환 |

---

## 3. 장점

- **문제가 분명함**: 스크린샷 → 앱 전환 → 그리기 → 저장의 여러 단계를 “지금 화면에 바로 낙서”로 줄임
- **원본 보존**: 레이어 위에만 그리므로 원본 페이지/앱은 건드리지 않음 (심리적 부담 감소, 구현도 오버레이만 다루면 됨)
- **페이지별 고정**: “이 주석은 이 화면에만 붙어 있다”는 식으로 설계 가능 → “다시 이 화면 왔을 때 주석이 살아 있음”이라는 차별화된 경험
- **토글**: 필요할 때만 주석 레이어를 켜고 끌 수 있어 사용성이 좋음

---

## 4. 고려할 점

### 4.1 “핸드폰 옆 버튼”
- **물리 버튼**은 기기·제조사마다 다르고, OS가 이미 사용하는 경우가 많아 **일반 앱이 “주석 전용”으로 할당받기 어려움**
- **대안**: 볼륨 버튼 조합, 흔들기, **플로팅 버튼**, 알림/제스처 등으로 “주석 모드 진입”을 정의하는 방식이 현실적

### 4.2 적용 범위

#### 4.2.1 시스템 전체(모든 앱 화면)에 주석을 붙이려 할 때

**필요한 것**
- **오버레이 권한**: 다른 앱 화면 위에 반투명 레이어를 띄우려면 OS가 허용해야 함.
  - **Android**: `SYSTEM_ALERT_WINDOW`(다른 앱 위에 그리기) 권한 필요. 사용자가 설정에서 수동 허용해야 하며, 제조사·OS 버전마다 정책이 다름. Android 10+에서는 제한이 더 엄격해지는 추세.
  - **iOS**: 일반 앱은 **다른 앱 화면 위에 지속적으로 오버레이를 띄우는 것이 거의 불가능**에 가깝다. 화면 녹화/캡처도 제한적이고, 사용 중인 앱이 아닌 우리 앱으로 전환되면 레이어는 사라짐.
- **“현재 페이지”가 뭔지 알기 어려움**  
  - 다른 앱(카카오톡, 인스타, Chrome 등)이 지금 어떤 **화면(URL, 탭, 채팅방 ID 등)** 을 보여 주는지는, 우리 앱이 **직접 조회할 수 없음**.  
  - Android에서도 다른 앱의 화면 내용·구조에 접근하려면 **Accessibility 서비스** 같은 강한 권한이 필요하고, 개인정보·보안 이슈로 스토어 정책·사용자 거부감이 큼.  
  - 따라서 “이 주석은 정확히 어떤 페이지에 붙어 있는지”를 **앱 패키지명 + 대략적인 화면 추정** 정도로만 구분할 수 있어, **같은 앱 내 다른 화면**을 정확히 나누기 어렵다.

**정리**: 시스템 전체에서 “어디에든” 주석을 달고, 그 “페이지”를 정확히 기억해 다시 보여 주는 것은 **기술·권한·플랫폼 정책** 모두 부담이 크다.

#### 4.2.2 특정 앱(웹브라우저, PDF 리더 등) 안에서만 주석을 두는 경우

- **우리 앱이 그 화면을 직접 렌더링**하므로(웹뷰, PDF 뷰어 등), **현재 URL·문서 경로·페이지 번호**를 앱이 알고 있음.
- **레이어도 우리 앱 내부**에 두면 되므로, **시스템 오버레이 권한이 필요 없음**.
- “이 페이지에만 붙는 주석”을 **저장·불러오기**할 때도 **페이지 식별자(URL, documentId+page)** 를 정확히 쓸 수 있어, **같은 페이지 재방문 시 해당 주석만** 보이게 할 수 있음.

**정리**: 권한·구현·페이지 식별 모두 단순하고, “이 페이지/이 문서에만 붙는 주석”을 정확히 구현·검증하기 좋다.

---

#### 4.2.3 이 문제를 완화·해결하기 위한 방안

| 방안 | 설명 | 장점 | 한계 |
|------|------|------|------|
| **1) 우리 앱 내에서만 주석 (MVP)** | 웹뷰/PDF 뷰어 등을 우리 앱에 넣고, 그 안에서만 “페이지별 주석 레이어” 제공. | 권한 불필요, 페이지 식별 정확, 구현·검증 용이. | 사용자가 “우리 앱으로” 콘텐츠를 열어야 함. |
| **2) “이 앱에서 열기” 연동** | 다른 앱(Chrome, 파일 관리자 등)에서 **공유/열기**로 “우리 앱에서 보기” 선택 시, 우리 앱 내 웹뷰/뷰어로 URL·파일을 열고 그 안에서 주석. | 기존 앱에서 쓰던 페이지를 우리 앱으로 가져와 주석 환경만 우리가 제공. | 여전히 “우리 앱을 거쳐야” 함. |
| **3) Android 전용 시스템 오버레이** | Android만 대상으로, 오버레이 권한을 받아 **모든 화면 위**에 투명 레이어 띄우기. 페이지 식별은 **앱 패키지명 + (가능하면) 화면 스냅샷 해시** 등으로 대략 구분. | “어떤 앱이든” 화면 위에 바로 주석 가능. | iOS 불가, 페이지 식별이 부정확(같은 앱 내 다른 화면 구분 어려움), 권한 요청·정책 리스크. |
| **4) Accessibility 기반 (Android)** | Android Accessibility API로 “현재 포커스된 앱/뷰” 정보를 읽어, 그걸 페이지 식별자로 쓰기. | 이론상 “지금 보는 화면”을 더 정확히 구분할 수 있는 여지 있음. | 보안·개인정보 이슈 큼, 스토어 정책·사용자 거부감, 유지보수 부담. |
| **5) 브라우저 확장·PWA** | **Chrome 확장** 또는 **PWA**로 “이 웹페이지에만 붙는 주석”을 제공. 우리 서버에 URL별 주석 저장. | 데스크톱·모바일 웹에서 “페이지별 주석”을 같은 계정으로 쓸 수 있음. | “웹페이지”에만 해당, 네이티브 앱 화면에는 적용 안 됨. |

**실무적 추천**
- **먼저 1) + 2)**: “우리 앱/뷰어 안에서만 주석” + “다른 앱에서 우리 앱으로 열기”로, **페이지 단위 주석**을 안정적으로 구현하고 가치를 검증.
- **이후** 플랫폼·정책을 고려해 **3) Android 오버레이**를 “보조 모드”(예: 우리 앱에 없는 화면만 임시로 캡처+주석)처럼 제한적으로 도입하는 것을 검토할 수 있음.

### 4.3 저장·동기화
- 주석을 “페이지와 1:1”로 유지하려면  
  → 페이지 식별자(URL, 앱+화면 ID, 문서 경로 등)와 주석 데이터(좌표, 스트로크)를 저장하고, 같은 페이지 재방문 시 불러와야 함
- 기기 변경·앱 재설치를 고려하면 **저장 위치(로컬 vs 계정 연동)** 를 처음부터 설계하는 것이 좋음

### 4.4 유사 서비스
- Samsung Notes, 일부 브라우저/PDF 앱의 “화면에 그리기”, 스크린샷 후 바로 마크업 등 **“바로 그리기”에 가까운 경험**이 이미 존재
- 차별점은 **“페이지별로 붙어 있고, 다시 그 페이지에 오면 자동으로 보인다”** + **“원본은 절대 건드리지 않는다”**를 얼마나 명확·편하게 만들지에 있음

## 5. 구현 방향 제안

1. **진입 방식**  
   - 1차: **플로팅 버튼** 또는 **제스처**로 “주석 모드” 진입  
   - 물리 버튼은 “지원 가능한 기기에서의 확장”으로 두는 것이 무난

2. **적용 범위 (MVP)**  
   - **시스템 전체**보다는  
     **특정 영역**(예: 우리 앱 내 웹뷰, 또는 우리가 만든 브라우저/뷰어)에서  
     “이 페이지에만 붙는 투명 주석 레이어”를 먼저 구현  
   - 권한·페이지 식별·저장이 단순해지고, 검증하기 좋음

3. **데이터 구조 (개념)**  
   - `페이지 식별자` (URL 또는 앱 내 화면 ID)  
   - `주석 데이터` (스트로크 좌표, 색·두께, 텍스트 등)  
   - 같은 페이지 재방문 시 위 데이터를 불러와 레이어에 그리기

---

## 6. 정리

- **컨셉**: 투명 레이어 + 페이지별 기억 + 원본 비손상 → 설득력 있음
- **진입**: “핸드폰 옆 버튼”은 제약이 크므로, 우선 플로팅 버튼/제스처 등으로 정의하고 버튼은 옵션으로
- **범위**: 첫 버전은 “전체 화면”보다 “우리 앱/뷰어 내 특정 페이지”에 한정하면 구현·검증이 수월함
