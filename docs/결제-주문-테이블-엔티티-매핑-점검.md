# 결제·주문 관련 테이블 ↔ 엔티티 매핑 점검

## 1. orders 테이블

### 스키마 (data.sql + 마이그레이션)
| 컬럼 | 출처 | NOT NULL | 엔티티 필드 | 저장 시 설정 |
|------|------|----------|-------------|--------------|
| id | data.sql | PK | id | IDENTITY |
| user_id | data.sql | | userId | O (주문자) |
| guest_email | data.sql | | guestEmail | O |
| guest_phone | data.sql | | guestPhone | O |
| status | data.sql | O, DEFAULT | status | O |
| total_amount | data.sql | O, DEFAULT | totalAmount | O |
| applied_user_coupon_id | V2 | | appliedUserCouponId | O (수정 시) |
| created_at | data.sql | | createdAt | O |
| updated_at | data.sql | | updatedAt | O |
| customer_id | V5 | nullable로 변경 | customerId | O (userId와 동일) |
| order_number | V6 또는 배포 DB | 배포 시 NOT NULL 가능 | orderNumber | O (ORD-yyyyMMddHHmmss-XXXX) |
| total_price | V7 또는 배포 DB | 배포 시 NOT NULL 가능 | totalPrice | O (totalAmount와 동일) |
| payment_id | V8 (추가), V9 (VARCHAR→BIGINT) | nullable | paymentId | O (주문 생성 시 null, 결제 ready 시 payments.id) |
| type | V10 또는 배포 DB | NOT NULL (배포 시) | type | O (기본 'GENERAL') |

**결론**: 모든 컬럼 매핑됨. `order_number`, `total_price`, `customer_id`는 배포 DB NOT NULL 대응으로 저장 시 값 설정함. `payment_id`는 결제 준비 시 `PaymentService.ready()`에서 갱신·저장됨. `type`은 배포 DB에 NOT NULL 컬럼이 있으면 저장 시 'GENERAL' 등 설정(V10).

## 3. payments 테이블

### 스키마 (data.sql)
| 컬럼 | NOT NULL | 엔티티 필드 | 저장 시 설정 |
|------|----------|-------------|--------------|
| id | PK | id | IDENTITY |
| order_id | O, FK | orderId | O |
| method | O, DEFAULT | method | O (TOSS 기본) |
| status | O, DEFAULT | status | O (PENDING 기본) |
| pg_tid | | pgTid | O (완료 시) |
| amount | O, DEFAULT | amount | O (null 시 0) |
| paid_at | | paidAt | O (완료 시) |
| created_at | | createdAt | O |

**결론**: 모든 컬럼 매핑됨. `PaymentService.ready()`에서 amount null 방지, `PaymentPersistenceAdapter.toEntity()`에서 method/status/amount null 시 기본값 적용함.

---

## 4. 적용한 보완 사항

1. **PaymentService.ready()**  
   - `order.getTotalAmount()`가 null일 수 있어 `amount`를 `order.getTotalAmount() != null ? order.getTotalAmount() : 0`으로 설정하도록 수정.

2. **PaymentPersistenceAdapter.toEntity()**  
   - `method`, `status`, `amount`가 null이면 각각 `"TOSS"`, `"PENDING"`, `0`으로 설정해 DB NOT NULL/DEFAULT와 맞춤.

## 5. 요약

- **orders**: order_number, total_price, customer_id 포함해 모든 컬럼 엔티티 매핑·저장 로직 반영됨.
- **order_items**: 컬럼·매핑 일치, 누락 없음.
- **payments**: 컬럼·매핑 일치, amount 등 null 방지 처리 추가됨.

배포 DB에 위 테이블 외에 별도 컬럼이 있다면(예: Hibernate ddl-auto로 추가된 컬럼) 해당 컬럼을 엔티티에 추가하거나, 마이그레이션으로 스키마를 data.sql/엔티티와 맞추는 것이 좋습니다.

## 6. 결제 시스템 리뷰 요약

### 데이터·테이블·타입 정합성
- **orders**: `order_number`(V6), `total_price`(V7), `customer_id`(V5 nullable), `payment_id`(V8 추가, V9에서 VARCHAR→BIGINT 정리) 모두 엔티티·저장 로직과 일치.
- **order_items**: 컬럼·엔티티·DTO(OrderItemDto) 타입 일치. `optionExtraPrice` Integer/optional 처리 일관됨.
- **payments**: `amount`/`method`/`status` null 방지(PaymentService + PaymentPersistenceAdapter). `createdAt`은 Payment 도메인 생성 시 설정 후 toEntity에서 그대로 전달.

### 저장 시점
- **Order**: 생성 시 `orderNumber`, `totalPrice`(totalAmount와 동일), `customerId`(userId와 동일) 설정. 결제 ready 시 `paymentId` 갱신 후 `orderRepositoryPort.save(order)`.
- **Payment**: ready 시 `amount = order.getTotalAmount() != null ? order.getTotalAmount() : 0`, `createdAt = LocalDateTime.now()`.

### API·프론트
- **CreateOrderRequestDto**: userId(Long), items(List<OrderItemDto>), unitPrice/optionExtraPrice(Integer) — 백엔드와 일치.
- **orderService.ts**: CreateOrderPayload userId number | null, optionExtraPrice optional — 타입 호환.
- **payment_id**: 주문 응답에 필수는 아님. 결제 준비 응답에 `paymentId` 포함(processPaymentUseCase.ready).

### 주의사항
- **V9 마이그레이션**: `payment_id`가 기존에 VARCHAR이고 숫자 아닌 값이 있으면 `USING ...::BIGINT` 변환 시 예외 발생 가능. EXCEPTION WHEN OTHERS THEN NULL로 묶여 있어 실패 시 컬럼 타입이 바뀌지 않을 수 있음. 배포 DB에 숫자형 payment_id만 있다고 가정하고 사용.
- **data.sql**: 초기 데이터에 order_number/total_price/customer_id/payment_id가 없을 수 있음. 로컬은 마이그레이션(V5~V9) 적용 후 엔티티와 일치하므로, data.sql만으로 기동하는 환경은 해당 컬럼이 있거나 기본값/ nullable이어야 함.
